## Identity and Access Assessment

| # | Problematic Line(s) | Resource | Risk Level | CWE | MITRE ATT&CK | Exploitability | Impact | Suggested Fix |
|---|---------------------|----------|------------|-----|--------------|----------------|--------|---------------|
| 1 | Lines 215–219 (`aws_iam_role_policy.ec2policy`) | `s3:*`, `ec2:*`, `rds:*` on `Resource: "*"` | Critical | CWE-732 | T1552.005 | **Confirmed.** The policy is attached to `ec2role`, which backs the instance profile on `aws_instance.db_app`. Any code execution on the EC2 host — via the web application, a misconfigured SSH rule, or the exposed user_data (finding #2) — allows an attacker to call the IMDSv1 endpoint (`169.254.169.254/latest/meta-data/iam/security-credentials/`) with no authentication and obtain live STS credentials for the role. | Those credentials grant `s3:*`, `ec2:*`, and `rds:*` on `*` across the entire AWS account, enabling full data exfiltration, instance takeover, and database destruction. | Scope `Action` to the minimum operations the app actually requires (e.g., `s3:GetObject`, `rds:DescribeDBInstances`) and restrict `Resource` to specific ARNs. Also enforce IMDSv2 on the instance by setting `metadata_options { http_tokens = "required" }` to require a session token before credentials are vended. |
| 2 | Lines 265, `consts.tf:42` (`aws_instance.db_app` user_data + variable default) | `define('DB_PASSWORD', '${var.password}')` with default `"Aa1234321Bb"` | Critical | CWE-522 | T1552.001 | **Confirmed and worsened by cross-file finding.** The DB password is interpolated into EC2 `user_data` at plan time and stored unencrypted by AWS. Any IAM principal with `ec2:DescribeInstanceAttribute` can retrieve it via the AWS API. Separately, `consts.tf:42` sets `default = "Aa1234321Bb"` on `var.password` — meaning any deployment that does not explicitly override this variable uses a publicly known credential. This repository is public; the default is visible to anyone. | Combined with `username = "admin"` (finding #3) and `publicly_accessible = true` (Network finding #1), this is a complete, no-brute-force-required attack chain against the database endpoint. | Remove the default from `var.password` entirely so an explicit value is always required. Retrieve the secret at runtime from AWS Secrets Manager or SSM Parameter Store (SecureString) rather than injecting it via `user_data`. |
| 3 | Lines 14, `consts.tf:42` (`aws_db_instance.default` + variable default) | `username = "admin"` with default password `"Aa1234321Bb"` | High | CWE-1392 | T1078.001 | **Confirmed.** `username = "admin"` is a well-known default, and cross-referencing `consts.tf:42` reveals the default password is `"Aa1234321Bb"` — hardcoded in a public repository. Any deployment using the default variable values presents a fully known credential pair. | With the database publicly accessible (Network finding #1), an attacker can attempt `mysql -h <endpoint> -u admin -pAa1234321Bb` directly, with no need for any prior reconnaissance or brute force. Previously assessed as Low (predictable username only); upgraded to High based on the confirmed default credential. | Remove the default from `var.password`. Use a randomly generated username (e.g., via `random_string`) rather than a static `"admin"`. |
| 4 | Missing attribute at db-app.tf:243 (`aws_instance.db_app`) | No `metadata_options` block — IMDSv1 active | High | CWE-306 | T1552.005 | **Confirmed.** No `metadata_options` block appears anywhere in the `aws_instance.db_app` resource. AWS defaults to IMDSv1, which allows any process on the instance to retrieve IAM credentials from `http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>` using a plain HTTP GET — no session token required. Any code execution on the instance (shell access via open SSH port, Network finding #6, PHP vulnerability, or command injection) immediately yields live STS credentials for `ec2role`. | Given the wildcard IAM policy (finding #1), this translates directly to full account access with zero additional steps. | Add `metadata_options { http_tokens = "required" http_endpoint = "enabled" }` to enforce IMDSv2. IMDSv2 requires a `PUT` to obtain a session token before credentials can be fetched, blocking credential theft via SSRF and one-shot curl commands from a web shell. |

## Data & Storage Assessment

| # | Problematic Line(s) | Resource | Risk Level | CWE | MITRE ATT&CK | Exploitability | Impact | Suggested Fix |
|---|---------------------|----------|------------|-----|--------------|----------------|--------|---------------|
| 1 | Line 19 (`aws_db_instance.default`) | `storage_encrypted = false` | Critical | CWE-311 | T1578.001 | **Confirmed.** RDS stores all data — table files, redo logs, and any snapshots — on unencrypted EBS volumes. An attacker who gains access to a snapshot (e.g., through a misconfigured `aws_db_snapshot` sharing policy, a cross-account share, or a pipeline that copies snapshots to an insecure bucket) reads all data in plaintext with no decryption step required. | This is compounded by the absence of backups (Long-Term Controls #1): manual snapshots are the only copy mechanism, making each one a high-value unencrypted target. Also intersects with Network finding #1 — an unencrypted instance with a public endpoint exposes data through two independent paths simultaneously. | Set `storage_encrypted = true`. Specify a customer-managed KMS key via `kms_key_id` (see Long-Term Controls #4) so that key policy, rotation, and revocation remain under your control. Note: encryption cannot be enabled on a running instance — a snapshot-restore into a new encrypted instance is required. |

## Network Egress and Ingress Assessment

| # | Problematic Line(s) | Resource | Risk Level | CWE | MITRE ATT&CK | Exploitability | Impact | Suggested Fix |
|---|---------------------|----------|------------|-----|--------------|----------------|--------|---------------|
| 1 | Line 22 (`aws_db_instance.default`) | `publicly_accessible = true` | Critical | CWE-668 | T1190 | **Conditional.** AWS assigns a public DNS hostname and public IP to the RDS instance. The SG ingress rule (db-app.tf:141) currently restricts port 3306 to `aws_vpc.web_vpc.cidr_block` (`172.16.0.0/16`), so internet traffic is blocked at the SG layer today. However, this is one `aws_security_group_rule` change away from full internet exposure — and any IAM principal with `ec2:AuthorizeSecurityGroupIngress` can make that change without touching Terraform. | Confirmed against ec2.tf:176–228: an internet gateway (`web_igw`) and public route (`0.0.0.0/0 → web_igw`) already exist, so the routing path to the instance requires zero infrastructure additions. | Set `publicly_accessible = false`. The SG is a necessary control but insufficient alone — eliminate the public endpoint so no route to 3306 exists at the network layer regardless of SG state. |
| 2 | Lines 99, 211–217 (`aws_db_subnet_group.default` + `ec2.tf`) | `subnet_ids` references `web_subnet` and `web_subnet2` | High | CWE-668 | T1190 | **Confirmed.** Cross-file verification against ec2.tf proves both subnets are internet-facing public subnets: `map_public_ip_on_launch = true` (ec2.tf:139, 159), associated with route table `web_rtb` (ec2.tf:210–217), which has an explicit `0.0.0.0/0 → web_igw` route (ec2.tf:220–223). | The RDS instance is placed directly on the same internet-routable subnet tier as the load balancer and EC2 web host. Any compromise of the web tier grants immediate same-subnet access to the database with no routing boundary to cross. | Create dedicated private database subnets with no IGW association and `map_public_ip_on_launch = false`, backed by a route table with only local VPC routes. Reference only those subnets in the DB subnet group. |
| 3 | Lines 145–152 (`aws_security_group_rule.egress`) | `protocol = "-1"`, `cidr_blocks = ["0.0.0.0/0"]` | Medium | CWE-923 | T1048 | **Misconfiguration confirmed; direct RDS exploitability is limited.** The egress rule is present as stated, but RDS is a managed service — there is no OS access to the instance, and the MySQL 8.0 engine cannot initiate arbitrary outbound TCP connections (no custom UDFs, no `LOAD DATA FROM URL` on standard RDS). The realistic risks are: (a) if a future EC2 or Lambda resource is accidentally associated with this same security group, it inherits unrestricted outbound access; (b) the open egress removes a control that would otherwise block certain AWS RDS integrations from phoning home unexpectedly. | Downgraded from High on the basis that the managed service boundary limits engine-level outbound exploitation. | Replace the catch-all rule with a targeted allow-list scoped to the specific AWS service endpoints RDS requires (e.g., CloudWatch for monitoring, KMS for encryption). Use AWS-managed prefix lists rather than `0.0.0.0/0`. |
| 4 | Lines 65–95 (`aws_db_parameter_group.default`) | `require_secure_transport` not set in parameter group | Medium | CWE-319 | T1040 | **Confirmed and exploitable within the VPC.** The parameter group sets only `character_set_client` and `character_set_server`; `require_secure_transport` is absent, meaning MySQL defaults it to `OFF`. Any client within the VPC (`172.16.0.0/16`) — including the EC2 instance in `web_subnet` — can establish a plaintext MySQL session. | An attacker with access to the VPC (e.g., via the EC2 web host, a VPC peer, or a shared subnet resource) can perform a passive MITM to harvest credentials and query results in transit. | Add `{ name = "require_secure_transport", value = "ON", apply_method = "immediate" }` to the parameter group. Set `ca_cert_identifier` on the RDS instance to enforce server certificate validation on the client side. |
| 5 | Lines 97–115 (`aws_db_subnet_group.default`) | No `aws_network_acl` defined for database subnets | Low | CWE-284 | T1562.007 | **Confirmed; exploitability is indirect.** A search across all `.tf` files in `terraform/aws/` finds no `aws_network_acl` resource. AWS applies the default NACL to all subnets without an explicit association, and the default NACL permits all inbound and outbound traffic. Security groups are therefore the only enforcement layer. | If any SG rule is misconfigured or overly broad (as with finding #3), there is no secondary stateless control at the subnet boundary to contain the exposure. | Define a dedicated `aws_network_acl` for the database subnets allowing inbound TCP 3306 only from the application subnet CIDR and denying all else. Attach it via `aws_network_acl_association`. |
| 6 | `ec2.tf:90–96`, referenced at db-app.tf:250 (`aws_security_group.web-node`) | SSH port 22 open to `0.0.0.0/0` | Critical | CWE-284 | T1021.004 | **Confirmed.** The `aws_instance.db_app` resource (db-app.tf:249–250) attaches `aws_security_group.web-node`, which is defined in ec2.tf and contains an ingress rule allowing TCP 22 from `0.0.0.0/0`. The instance is placed in `web_subnet` with `map_public_ip_on_launch = true` and an IGW route, so it receives a public IP at launch. Any host on the internet can reach the SSH daemon directly. | The instance holds plaintext DB credentials on disk (`/var/www/inc/dbinfo.inc`) and an IAM instance profile with `s3:*`, `ec2:*`, `rds:*` — SSH access is a full-account-compromise entry point. | Restrict the SSH ingress rule to a known management CIDR (e.g., a VPN egress IP or bastion host SG). Do not allow `0.0.0.0/0` on port 22. For automated deployments, remove SSH entirely and use AWS Systems Manager Session Manager, which requires no open inbound port. |

> **Cross-file note (ec2.tf:15–16):** `aws_instance.web_host` exports `AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMAAA` and `AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMAAAKEY` in plaintext `user_data`. These are the canonical AWS documentation example credentials and are not live credentials; however the pattern is flagged by SAST tooling and any principal with `ec2:DescribeInstanceAttribute` can retrieve them via the AWS API. `web_host` shares `aws_security_group.web-node` (SSH open to `0.0.0.0/0`), `web_subnet`, and `web_vpc` with `db_app`, so it sits in the same lateral-movement blast radius. A separate review of ec2.tf is warranted.

> **Priority Remediation — Findings #1 & #2 (Combined):** `publicly_accessible = true` combined with placement in fully internet-routable public subnets (`map_public_ip_on_launch = true`, `0.0.0.0/0 → web_igw` route confirmed in ec2.tf) means the network path from the public internet to the RDS endpoint already exists at the routing level. The SG ingress restriction to `172.16.0.0/16` is currently the only control preventing exploitation. A single IAM call (`ec2:AuthorizeSecurityGroupIngress`) removes that control entirely. Remediate by setting `publicly_accessible = false` and migrating to private subnets — both must be fixed together to actually eliminate the attack surface.

## Long-Term Controls

Controls in this section do not represent directly exploitable vulnerabilities. They reduce attacker dwell time, improve incident response capability, and support compliance obligations. They should be planned alongside — not instead of — remediating the findings above.

| # | Priority | Affected Resource | Gap | Recommended Control |
|---|----------|-------------------|-----|---------------------|
| 1 | **P1** | Lines 39–41 (`aws_db_instance.default`) — `lifecycle { ignore_changes = ["password"] }` | Terraform is permanently configured to ignore the `password` attribute on the RDS instance. Any change to `var.password` in future will be silently discarded on `terraform apply`. If the default credential `"Aa1234321Bb"` (consts.tf:42) was used at first deployment, it cannot be rotated through the IaC pipeline without manually removing this lifecycle block. This does not enable external exploitation on its own — it **prevents remediation of IAM finding #3** (default credential), making this a remediation blocker for an active Critical finding. | Remove the `ignore_changes = ["password"]` lifecycle block. Manage the password exclusively via AWS Secrets Manager with automatic rotation enabled; the application should retrieve it at runtime rather than receiving it as a Terraform variable. |
| 2 | **P1** | Line 18 (`aws_db_instance.default`) — `backup_retention_period = 0` | Automated backups and point-in-time recovery (PITR) are fully disabled. This does not enable an attacker to do anything they could not already do, but it eliminates every native AWS recovery path. Any successful attack that corrupts or destroys data — ransomware, a destructive SQL statement, or exploitation of the `rds:*` wildcard (IAM finding #1) — has no rollback option. | Set `backup_retention_period` to at least `7` days (`35` for regulated workloads). Set `backup_window` to a low-traffic period. Enabling backups also re-enables PITR, which is the primary recovery tool for row- or table-level corruption. |
| 3 | **P1** | Line 20 (`aws_db_instance.default`) — `skip_final_snapshot = true` | No snapshot is taken when the instance is destroyed. Combined with disabled automated backups (control #2), any `terraform destroy`, accidental deletion, or exploitation of the `rds:DeleteDBInstance` permission (available via the IAM wildcard in IAM finding #1) results in permanent, unrecoverable data loss. Not exploitable on its own — destruction still requires AWS API access — but removes the last recovery backstop. | Set `skip_final_snapshot = false` and specify a `final_snapshot_identifier`. This ensures a point-in-time copy exists even if the instance is deleted. |
| 4 | **P1** | Missing attribute (`aws_db_instance.default`) — `deletion_protection` not set (defaults to `false`) | The database can be deleted by a single `rds:DeleteDBInstance` API call with no additional confirmation step. The IAM wildcard (IAM finding #1) grants this permission to any principal that compromises the EC2 host. Without deletion protection, destruction is a single-step operation; with it enabled, an attacker must also call `rds:ModifyDBInstance` to disable the flag first, adding friction. Not independently exploitable, but reduces the cost of destruction when combined with the IAM finding. | Set `deletion_protection = true`. Pair with controls #2 and #3 to ensure that even if deletion occurs, a recovery path exists. |
| 5 | **P2** | Line 21 (`aws_db_instance.default`) — `monitoring_interval = 0` | Enhanced Monitoring is disabled. No OS-level metrics (CPU, memory, network I/O) are published to CloudWatch Logs, eliminating the baseline needed to detect anomalous connection volume, query throughput spikes, or resource exhaustion caused by active attacks. | Set `monitoring_interval = 60` (or `10` for higher fidelity). Attach an IAM role with `AmazonRDSEnhancedMonitoringRole` via `monitoring_role_arn`. Set CloudWatch alarms on `DatabaseConnections` and `NetworkReceiveThroughput` to catch anomalies. |
| 6 | **P2** | Missing attribute (`aws_db_instance.default`) — `iam_database_authentication_enabled` not set | RDS defaults to static password-only authentication. Without IAM DB auth, there is no mechanism to issue short-lived credentials to the EC2 role, making rotation difficult to enforce and connection auditing coarse-grained. Not an attack vector on its own — an attacker still needs valid credentials — but its absence makes credential hygiene harder to sustain. | Set `iam_database_authentication_enabled = true`. Grant the EC2 role the `rds-db:connect` action scoped to the specific DB user ARN. This enables the application to authenticate without a long-lived password at runtime. |
| 7 | **P3** | Line 171 (`aws_iam_role.ec2role`) — no `permissions_boundary` | Without a permissions boundary, the effective permissions of `ec2role` are bounded only by whatever policies are currently attached. No ceiling exists to prevent a future policy addition — intentional or accidental — from expanding the role beyond its intended scope. Not directly exploitable without an additional misconfiguration, but increases blast radius if IAM write access is compromised. | Define an `aws_iam_policy` that acts as a permission ceiling (e.g., allowing only the S3/RDS/EC2 namespaces actually needed) and attach it as `permissions_boundary` on the role. The boundary does not grant permissions — it caps what any attached policy can grant. |
| 8 | **P3** | Missing attribute (`aws_db_instance.default`) — `kms_key_id` not set | Once `storage_encrypted = true` is enabled (Data & Storage finding #1), the instance will use the AWS-managed `aws/rds` key by default. This key cannot be disabled, has no custom key policy, does not support cross-account access restrictions, and cannot be used to cryptographically revoke access by key deletion. It is not an independent vulnerability, but it limits the operational controls available over encrypted data. Gated on the Data & Storage finding being remediated first. | Create a dedicated `aws_kms_key` with a restrictive key policy (deny `kms:*` to all principals except the RDS service role and designated admins) and reference it via `kms_key_id`. Address this at the same time as enabling encryption — changing the KMS key after the fact requires another snapshot-restore cycle. |
| 9 | **P4** | Line 17 (`aws_db_instance.default`) — `multi_az = false` | No standby replica exists in a second Availability Zone. An AZ-level failure causes full database unavailability with no automatic failover. This is an availability gap, not a security vulnerability — an attacker cannot exploit single-AZ placement to gain access to data. Included here because AZ failures are a realistic operational event that amplifies the impact of any concurrent incident response effort. | Set `multi_az = true` to provision a synchronous standby. Failover is automatic and typically completes in under two minutes. Note: roughly doubles instance cost. |
