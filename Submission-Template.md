> **Top Defense in Depth Practice — RDS Network Perimeter ([db-app.tf](terraform/aws/db-app.tf))**
>
> The RDS `default` instance is the strongest DiD example in the codebase. Despite `publicly_accessible = true` ([db-app.tf:22](terraform/aws/db-app.tf#L22)) punching through the outer perimeter by assigning a public DNS endpoint, two independent inner layers held: a dedicated security group (`web_vpc-rds-sg`) scoped separately from the web-tier SG ([db-app.tf:117-134](terraform/aws/db-app.tf#L117-L134)), and an ingress rule that binds port 3306 to the VPC CIDR (`172.16.0.0/16`) rather than `0.0.0.0/0` ([db-app.tf:136-143](terraform/aws/db-app.tf#L136-L143)). An internet-sourced connection fails at the SG even though the DNS endpoint is routable — exactly what Defense in Depth is designed to do. The contrast is Elasticsearch (F-02/F-08), which also has no VPC placement but lacks any equivalent inner layers, resulting in full public exposure. The RDS example demonstrates that SG tier-separation and CIDR-scoped ingress are the two controls that matter most when an outer flag is misconfigured; both should be present by default on every data-tier resource.

> **Top Defense in Depth Practice — EKS IAM Role ([eks.tf:7-42](terraform/aws/eks.tf#L7-L42))**
>
> The EKS control-plane IAM role is the strongest identity DiD example in the codebase. It stacks four independent controls: (1) a structured trust policy written as an `aws_iam_policy_document` data source rather than inline JSON — type-checked by Terraform, preventing accidental wildcard principals; (2) trust scoped exclusively to `eks.amazonaws.com`, meaning no human user, cross-account principal, or other service can assume the role; (3) permissions attached via named AWS-managed policy ARNs (`AmazonEKSClusterPolicy`, `AmazonEKSServicePolicy`) rather than inline wildcard statements — providing a clear, auditable permission set; and (4) explicit `depends_on` ordering on the policy attachments, ensuring the role is fully configured before the cluster assumes it and eliminating a privilege-escalation window during provisioning. Compare this to the EC2 instance role in [db-app.tf:210-226](terraform/aws/db-app.tf#L210-L226), which grants `s3:*`, `ec2:*`, `rds:*` on `Resource: "*"` via inline JSON with no scoping — a single SSRF vulnerability would yield near-total account control. The EKS pattern is the template every other role in this configuration should follow.

> **Top Defense in Depth Practice — `logs` bucket + `data_science` access logging + dedicated KMS key ([s3.tf:89-141](terraform/aws/s3.tf#L89-L141), [kms.tf:1-16](terraform/aws/kms.tf#L1-L16))**
>
> While most storage resources in this codebase omit controls entirely, the `logs` and `data_science` S3 buckets stack five independent defenses on the same data path. The `logs` bucket ([s3.tf:113-141](terraform/aws/s3.tf#L113-L141)) applies a restricted `log-delivery-write` ACL (blocking public access at the policy layer), enables versioning so deleted or overwritten objects are recoverable, and configures server-side encryption using `aws:kms` tied to a dedicated `aws_kms_key.logs_key` rather than the default AWS-managed key — meaning key policy controls access independently of IAM bucket policy. The `data_science` bucket ([s3.tf:89-111](terraform/aws/s3.tf#L89-L111)) adds a fifth layer: it ships its access logs to the hardened `logs` bucket, so an attacker who compromises `data_science` cannot cover their tracks by deleting logs in the same bucket. The result is that no single control failure exposes the full picture: bypassing the ACL still requires defeating KMS encryption; deleting objects is reversed by versioning; and the audit trail lives in a separately protected bucket the attacker would also need to compromise. Contrast this with `aws_s3_bucket.data` (finding #15), which omits all five controls and is confirmed public by a developer comment — demonstrating exactly what the absence of layering looks like. The gap that remains: `logs_key` has no `enable_key_rotation = true` (finding #30), `data_science` has no encryption of its own, and neither bucket has an `aws_s3_bucket_public_access_block` resource — showing that even the best example in this codebase is one step short of a complete stack.

## Attack Chain Analysis

Three end-to-end attack paths are documented below, each mapped to MITRE ATT&CK tactics and techniques. All three originate from the open internet with no prior access. Chain 1 is the most severe — it uses real, deployed credentials and reaches the production database in nine steps with no exploit code required.

### Chain 1 — Full Database Compromise via Public Repository

**Prerequisites:** None. Internet access only.

| Step | Tactic | MITRE Technique | Detail |
|------|--------|-----------------|--------|
| 1 | Initial Access | T1078.004 — Valid Accounts: Cloud | Read [consts.tf:39-43](terraform/aws/consts.tf#L39-L43) in the public GitHub repo; obtain `username = "admin"` and `password = "Aa1234321Bb"` |
| 2 | Credential Access | T1552.001 — Credentials in Files | Same commit history exposes AWS access keys in [ec2.tf:15-16](terraform/aws/ec2.tf#L15-L16) and [providers.tf:9-11](terraform/aws/providers.tf#L9-L11) |
| 3 | Initial Access | T1190 — Exploit Public-Facing Application | SSH to EC2 on port 22 — `web-node` SG allows `0.0.0.0/0` ([ec2.tf:90-96](terraform/aws/ec2.tf#L90-L96)); both instances are in a public subnet with IGW routing and `map_public_ip_on_launch = true` ([ec2.tf:139](terraform/aws/ec2.tf#L139)) |
